# 项目治理经验

> 本文档沉淀 Ember 在本轮治理与重构中的稳定经验。重点不是记录某次改了什么，而是说明以后遇到类似问题时该怎么判断、怎么推进、怎么收尾。

## 1. 先解决边界，再解决结构

目录、文件大小、模块位置通常不是根问题，真正的问题是边界不清。

判断顺序必须是：

1. 先识别职责是否混在一起
2. 再决定是否拆文件
3. 最后才决定是否拆目录

禁止直接“为了整齐”搬目录。

## 2. 编排层和领域层不要用同一把尺子

并不是所有模块都应该变成标准领域目录。

- 领域层：适合目录化，例如 `email/`、`user/`、`redemption/`
- 编排层：允许保留聚合入口，例如 `auth/` 即使拆成多文件，本质仍是编排层

判断标准不是“看起来统一不统一”，而是：

- 是否天然依赖多个服务
- 是否主要负责编排流程而不是承载稳定领域模型
- 是否目录化后真能降低复杂度

## 3. 过渡层可以存在，但必须提前写清退出条件

兼容层、适配层、临时桥接代码都允许短期存在，但必须明确：

- 为什么要引入
- 什么时候删除
- 删除前提是什么

没有退出条件的过渡层，最后一定会变成常驻层。

## 4. 重构完成必须同时满足三件事

只改代码不算完成，至少要同时满足：

1. 代码结构与调用面已收口
2. `go test ./...` 和 `go build ./...` 通过
3. 现行文档已经同步

缺任意一项，都不应宣称“已经完成”。

## 5. 为测试做轻量依赖注入是允许的

核心链路如果不可测试，后续重构就没有兜底。

允许做的事：

- 给服务增加轻量依赖注入点
- 把大函数里的纯判断逻辑拆成可测试小函数
- 为测试引入最小 stub 接口

不允许做的事：

- 为了测试把生产逻辑改成另一套设计
- 引入超出问题范围的大型抽象层

## 6. 计划文档要支持收尾，不只是支持开工

计划文档不能只会描述“准备做什么”，还必须能表达：

- 哪些已经完成
- 哪些被接受为不再继续推进
- 哪些条件满足后可以归档

建议至少使用这些状态：

- 草稿
- 收尾中
- 已完成

## 7. 归档条件必须明确

文档可以归档，至少说明：

- 主体结构是否已落地
- 是否完成编译与测试验证
- 是否接受当前测试覆盖作为收尾条件
- 现行文档是否已经同步

如果这些问题没有答案，就不要归档。

## 8. 文档必须和代码一起收口

代码一旦变了，文档也必须一起变。

至少要同步：

- `docs/system-architecture.md`
- 相关 `docs/reference/` 规范
- 对应的 `docs/proposals/` 或 `docs/plan/`

否则下一轮治理会直接建立在错误前提上。

## 9. 只在真实维护痛点存在时再继续治理

当结构已经足够清楚时，不要为了“彻底统一”继续重构。

继续治理的前提应当是：

- 真实维护成本高
- 变更经常踩边界
- 调用面持续扩散
- 测试和文档已经兜不住当前复杂度

如果只是“看起来还可以再整齐一点”，那通常不值得继续动。
