# 归档治理规范

本规范用于约束 Ember 文档进入 `docs/archive/` 时的分类方式、收尾动作和校验要求，避免“正文归档了，但索引、状态、引用仍停留在旧结构”。

## 1. 核心原则

- 先按文档类型分类，再按职责边界分类。
- 归档目录不按历史来源分类，不要保留按来源命名的目录。
- 归档动作不是“移动文件”这么简单，必须连同索引、状态、交叉引用一起收口。
- 已归档文档只保留追溯价值，不应继续承担现行规则或当前实现说明。

## 2. 一级目录分类

`docs/archive/` 一级目录固定按文档类型划分：

- `plan/`：已完成或退场的历史实施方案
- `proposal/`：已退场的治理/重构提案
- `report/`：总结、复盘、历史测试报告
- `reference/`：旧版但仍需追溯的参考材料
- `mvp/`：MVP 阶段历史资料

不要把不同类型的文档混放在 `docs/archive/` 根目录。

## 3. plan 子目录分类

`docs/archive/plan/` 下按 Ember 当前职责边界分类，而不是按来源项目、优先级或历史阶段分类。

当前标准分类为：

- `access-auth/`
- `billing-redemption/`
- `media-subscription/`
- `bot-telegram/`
- `console-admin/`
- `architecture/`

新增历史实施方案时，优先落入上述职责目录；不要再创建按历史来源命名的子目录。

## 4. 文件命名规则

- 文件名统一使用小写 `kebab-case`
- 禁止保留全大写历史命名，如 `OPEN-REGISTRATION-REDEMPTION-CODE.md`
- 若旧文档命名不符合规范，迁移归档时一并改名

## 5. 计划文档归档前收尾要求

计划文档在进入归档前，至少完成以下收尾：

1. 状态与正文一致
- `草稿`、`进行中`、`待补充` 这类状态必须清理
- 已完成文档应明确写 `已完成` 或 `已归档`

2. 当前事实与代码一致
- 过期的默认值、交互说明、实现范围必须修正
- 不能保留“第一版暂不支持”这类已经失效的描述

3. 验证清单收口
- 已完成项明确勾选
- 关键验证命令和真实验证结果补齐

4. 归档条件写清楚
- 哪些稳定结论已经提炼到 `docs/system-architecture.md`、`docs/reference/` 或 `docs/runbooks/`
- 为什么这份文档现在只剩追溯价值

## 6. 归档时必须同步更新的文件

归档动作必须同步检查并更新：

- `docs/archive/README.md`
- 原目录下的 `README.md`
- `docs/proposals/plan-inventory.md`
- `docs/proposals/README.md`
- 所有直接引用旧路径的 `docs/reference/`、`docs/runbooks/`、公开说明文档

如果只移动正文，不更新这些入口文档，归档不算完成。

## 7. 盘点文档写法要求

在盘点、索引或统计类文档中：

- 优先使用当前语义名称或当前归档分类路径
- 不要继续保留已经失效的来源前缀。
- “建议动作”列应写到具体分类目录，不要笼统写 `docs/archive/plan/`

## 8. 迁移后校验清单

归档或重组目录后，至少执行一次全局检查：

1. 检查旧路径残留

```bash
rg "旧目录名|旧文件路径" docs README.md .github
```

2. 检查过期状态词

```bash
rg "草稿|待归档|未落地|第一版暂不支持" docs
```

3. 检查新目录树是否符合预期

```bash
find docs/archive -maxdepth 3 -type d | sort
find docs/archive -maxdepth 3 -type f | sort
```

4. 检查 Git 是否识别为迁移而不是意外删除

```bash
git status --short
git diff --stat
```

## 9. 判断规则

遇到文档去留问题时，按下面顺序判断：

1. 它描述的是当前事实，还是历史过程？
2. 它是规则、方案、复盘、旧参考，还是阶段资料？
3. 如果进入归档，应该按哪类文档归档？
4. 如果继续保留在现行目录，它是否仍然指导当前决策？

回答不清这些问题时，不要先搬文件；先把类型和边界说清楚再动。
