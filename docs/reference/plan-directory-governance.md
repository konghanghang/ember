# `docs/plan/` 目录治理规范

本规范用于约束 Ember 新增计划文档在 `docs/plan/` 下的落位方式，避免计划文档再次回到“全部平铺在根目录、靠文件名猜边界”的状态。

## 1. 核心原则

- `docs/plan/` 与 `docs/archive/plan/` 使用同一套职责边界。
- 新计划文档优先按职责目录落位，不再默认平铺在 `docs/plan/` 根目录。
- 旧计划文档只在被再次修改或迁移时顺手归类，不做纯路径整理式搬迁。
- `docs/plan/` 根目录只保留入口和模板，不承载常规功能方案正文。

## 2. 标准目录

`docs/plan/` 当前标准分类为：

- `access-auth/`
- `billing-redemption/`
- `media-subscription/`
- `bot-telegram/`
- `console-admin/`
- `architecture/`

新增计划文档时，优先落入上述职责目录之一。

## 3. 落位规则

1. 与注册、登录、邮箱验证、密码、账号门控相关的计划，放 `access-auth/`
2. 与支付、兑换码、账单、续期相关的计划，放 `billing-redemption/`
3. 与媒体、订阅、追剧、排行榜、片库相关的计划，放 `media-subscription/`
4. 与 Telegram、Bot、通知、菜单、轮询/webhook 相关的计划，放 `bot-telegram/`
5. 与控制台、后台管理、设备、头像、模板用户、用户画像等相关的计划，放 `console-admin/`
6. 与系统结构、目录边界、配置中心、服务边界重构相关的计划，放 `architecture/`

如果一个计划横跨多个职责边界，按主链路归属放置，不新增“综合”目录。

## 4. 根目录保留项

`docs/plan/` 根目录只保留：

- `README.md`
- `plan-template.md`

不要把新的功能方案直接放回根目录。

## 5. 文件命名

- 文件名统一使用小写 `kebab-case`
- 不要保留大写缩写式命名
- 名称优先表达功能主题，不表达历史来源

## 6. 与归档目录的关系

- 计划落地后，进入 `docs/archive/plan/` 时沿用同一职责分类
- 不要在归档时重新发明目录边界
- 如果 `docs/archive/plan/` 已经存在对应职责目录，直接迁入

## 7. 迁移策略

- 新建计划文档：立即按本规范落位
- 旧计划文档：仅在再次修改、归档或清理时顺手迁移
- 不为了目录整齐单独发起一轮批量搬迁

## 8. 同步要求

调整 `docs/plan/` 目录或新增职责目录时，必须同步更新：

- `docs/plan/README.md`
- 相关协作入口文档（如 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`）
- 与计划目录直接相关的盘点或治理文档

## 9. 判断顺序

新增计划文档前，按下面顺序判断：

1. 它属于哪个职责边界？
2. 现有标准目录里是否已有对应位置？
3. 是否真的需要新增目录？
4. 如果后续归档，它会落到哪个 archive 子目录？

回答不清这些问题时，不要先创建新目录；先明确边界再落文档。
