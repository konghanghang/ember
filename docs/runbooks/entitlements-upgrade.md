# 套餐分组权益升级与验收

> 负责人：Ember
> 更新时间：2026-10-25

本次升级涉及 `20261004_01_plan_group_entitlements.sql`。代码采用统一套餐目录、多组独立权益和定时回退；不包含新的实时到期调度。

本手册承接[套餐与分组权益改版计划](../archive/plan/billing-redemption/plan-group-entitlements.md)归档后的升级规则和剩余业务/运维验收。历史实现、本地页面、隔离 PostgreSQL 和 Stripe 沙盒证据各自按对应版本保留，不等同于生产业务验收。

## 升级前

1. 备份 PostgreSQL，记录当前分组、用户期限及人工封禁状态。升级窗口内停止旧版 API/Gateway 写入，避免旧实例继续只修改用户单一到期时间。
2. 检查用户显式分组存在、空分组能解析到唯一默认分组；迁移发现普通用户分组无法解析时会拒绝执行，不自动扩大或丢弃授权。
3. 预先确定每组的权益等级与逐级媒体库包含关系。不要用展示排序代替权益等级。
4. 明确历史兑换码将全部失效，包含注册与续期；历史兑换记录、使用次数和已发放权益保留。

## 切换行为

- API 既有启动迁移器在事务内应用 SQL，无需 `AUTO_MIGRATE`。新表为 `user_entitlements`、`entitlement_events`，商品保存唯一 `plan_group/validity_type/days`，订单保留 `benefits` 快照；另加用户访问投影和人工处理字段。
- 用户按切换时已有分组和到期时间迁移；空期限按旧实现的永久语义映射。不得再次按历史订单累计发放。人工账号停用、Emby 人工封禁及远端同步状态不重置。
- 旧套餐按原分组和正数天数转换为单项限时权益；异常套餐须管理员修正。旧订单不伪造购买权益，已 completed 不重放，迟到成功且缺快照的订单进入待人工处理。
- 分组等级默认未配置。升级后由管理员在“用户分组 / 权益模板 → 权益等级”填写完整等级映射，校验媒体库包含关系成功后才能新购；用户仍能查看目录及已有权益。
- 管理员通过用户列表“权益”入口新增、延长、设置永久/到期或撤销某组权益；“编辑用户”支持更换当前分组，原期限和状态不变；目标组已有权益则拒绝覆盖。现有账号停用操作不删除权益。
- 待人工处理订单在支付记录中筛选；“记录线下已退款”只记录已完成的外部处理，不调用 Stripe；“发放补偿权益”与处理状态事务提交，重复请求不重复发放。

## 到期及权限

保留现有 `CRON_SCHEDULE`（可每日多个时点）、`CRON_ENABLED`、`CRON_TIMEZONE`。允许权益期限到达后等待下一轮检查；不新增每分钟到期轮询、请求时重算或启动兜底。支付/兑换/人工调整属于主动变更，仍同步更新生效结果。

任务执行时重读用户最新权益，有低等级有效权益则回退，否则停用；过期旧用户远端尚未停用时仍会进入检查。媒体库、求片、115 来源模式/并发/配额都跟随当前生效组，不合并、不清零用量。Emby 同步失败继续使用已有失败记录和人工重试入口，不能将本地授权成功当作远端已完成。

## 验收入口

- 默认 mock 测试不启动服务，不访问 Emby、Stripe、Telegram、115。
- 专用 PostgreSQL 验证须设置 `EMBER_INTEGRATION_DATABASE_URL` 指向隔离测试库，在 `services/api` 工作目录执行 `go test ./internal/app -run '^TestIntegrationEntitlementMigrationAndFallback$' -count=1 -v`。用例使用既有独立 schema harness，并在退出时清理测试 schema。
- 覆盖永久基础 + 限时全资源、同组追加、跨组独立期限、重复发放、到期回退、迁移重跑及新码不被重复失效。
- 目标 Emby Server 已确认 4.9.3.0；只复用已核对的 Policy 接口，未承诺远端会话立即中断。真实验证需另行明确授权。
- 2026-10-04 首轮实现及验收修复（`c20080cc`、`a219512` 对应阶段）已在专用测试库执行权益、旧数据回填与支付的 6 个 PostgreSQL 集成用例并通过，覆盖实际迁移及重跑；临时 schema 已清理。单组收敛的 9 个用例结果见下文；历史记录也见[测试手册](./testing.md#分组权益改版专项)，不代表在当前版本或生产数据库重新执行。

## 恢复边界

不要将旧版 API/Gateway 直接接回已经有新权益写入的数据库，旧程序不理解多权益和人工处理状态。需要回退时先停写，再按升级前备份与新增订单/权益记录制定恢复步骤；新产生的付款不能通过简单恢复旧备份而丢弃。常规修复沿用新增前向 SQL，不修改已经部署记账的迁移文件。

此处记录 2026-10-04 本地验收阶段的历史处理：当时功能尚未部署，按用户明确授权原地修订同一 SQL，不新增过程迁移。已执行首轮旧稿的测试库先停止旧 API/Gateway、备份，再明确处理组合商品并在事务内应用最终 SQL。只在结构和保留数据校验通过后更新该文件的 checksum；全局迁移器校验不变，其他已记账迁移不可修改。此历史操作不授权改写已部署环境的 SQL 或迁移记录；当前使用最终版预览镜像且已执行迁移的环境，切换稳定镜像时应保持相同 SQL checksum，不能重做回填。

本次测试 D 明确转换为增强分组 30 天并下架。新商品使用单组字段，新订单生成单项快照；历史组合订单、用户多组权益、审计和兑换历史保留。遇到未明确处置的多项商品时 SQL 拒绝转换，不能自动取第一项。永久明确写 `permanent/0`，异常 0 天旧商品不猜测为永久。
