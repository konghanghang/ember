# Ember 项目成熟度改进路线提案

> 状态：草稿
> 负责人：Ember
> 更新时间：2026-08-30

## 问题

Ember 已经从单一的 Emby 用户管理工具扩展为覆盖注册、账号生命周期、套餐支付、媒体库权限、求片订阅、MoviePilot 下载、播放分析和 Telegram 通知的完整系统。现阶段的主要矛盾已经不再是“功能不够”，而是工程与产品收口速度开始落后于功能增长速度：

- 产品实际能力已经超过“Emby 用户管理系统”的现有定位，外部用户难以快速理解 Ember 与邀请工具、求片工具之间的差异。
- API、Web、Bot 的基础测试和发布流程已经建立，但 release tag、三端镜像构建与测试结果尚未形成原子发布门禁。
- 核心领域代码集中在少数超大文件中，继续横向增加功能会提高修改成本和回归概率。
- PostgreSQL 集成测试、Web + API 联调测试和测试产物已进入 CI，但本地完整回归仍依赖额外数据库环境，关键链路的可信度还不够低成本复现。
- 系统已经包含 cron、异步任务、外部调用、支付 webhook、通知与补偿任务，但运行期可观测性仍主要依赖日志和 `/health`。
- 安全基础已经覆盖密码哈希、JWT 失效、Turnstile、内部密钥和敏感配置加密，但全局限流、浏览器安全策略、依赖与镜像供应链治理仍有缺口。
- 开源协作入口、对外 API 文档和社区治理文件尚不完整，项目对单一维护者依赖较高。
- 少量计划文档与实际代码状态已经出现漂移，说明文档治理需要从“规则建立”转入“持续退场和收尾”。

## 目标

这个提案要解决：

1. 明确 Ember 下一阶段的产品定位和工程优先级，避免继续以零散功能推动项目演进。
2. 先收口发布可信度、核心代码复杂度、关键链路测试和运行期可观测性，再扩大功能面。
3. 建立从总纲提案到具体实施计划的拆分规则，让每个阶段都有明确完成标准和退场条件。
4. 降低项目对单一维护者经验和人工发布纪律的依赖。
5. 保持现有用户可见行为、部署方式和外部集成合同稳定，不以治理为名进行无收益重写。

## 不做的事

- 不把 API 拆成更多独立微服务；当前“模块化 Go 单体 + Web + Bot”的部署边界适合现有规模。
- 不以提高覆盖率数字为唯一目标，不要求所有包机械达到同一覆盖率。
- 不在本提案中直接设计具体数据库字段、API DTO、前端页面或监控指标名称；进入实施时再创建对应计划。
- 不为了国际化或多媒体服务器支持而立即改造现有 Emby 专用模型；是否扩展必须由目标用户和维护成本决定。
- 不把现有功能计划全部并入本提案；它们继续保留各自业务边界。
- 不以一次大重构替代渐进式收口，不改变未被明确要求的用户可见行为。

## 当前状态

### 1. 产品与系统边界

当前 Ember 已经具备以下完整链路：

```text
注册 / 邀请码
  → 套餐、兑换与支付
  → Emby 账号创建与生命周期
  → 媒体库权限与 Policy 同步
  → 求片审批与 MoviePilot 下载
  → Emby 入库回写
  → 播放排行、历史与用户画像
  → Web / Telegram 管理与通知
```

现有 README 将项目定义为“面向 Emby 的用户管理系统”，但实际能力已经接近“Emby 用户运营与媒体管理平台”。与同类项目相比：

- [Wizarr](https://github.com/wizarrrr/wizarr) 更聚焦邀请、引导、SSO 和多媒体服务器接入。
- [Seerr](https://github.com/seerr-team/seerr) 更聚焦媒体发现、求片和 Sonarr / Radarr 集成。
- [Ombi](https://github.com/Ombi-app/Ombi) 更聚焦成熟求片、用户通知和多端体验。
- Ember 的差异化在于把 Emby 用户运营、套餐支付、权限同步、求片下载和播放分析整合到同一系统。

| Bot `app` | 约 3900 行 |
| Go 测试文件 | 86 |
| Web 测试文件 | 13 |

当前主要复杂度热点：

### 3. 测试与验证

2026-07-12 本地基础验证结果：

- API：`go vet`、基础 `go test`、`go build` 通过；约 1037 个用例通过、10 个跳过；行覆盖率约 `38.9%`。
- Web：Vitest 和生产构建通过；58 个用例通过、3 个跳过；行覆盖率约 `56.35%`。
- Bot：`py_compile` 和 pytest 通过；43 个用例通过；当前测试脚本未产出覆盖率数字。
- 本地未提供 `EMBER_INTEGRATION_DATABASE_URL`，因此 API PostgreSQL 集成测试和 Web + API 联调测试被跳过。
- CI 已配置 PostgreSQL service，并通过现有 `scripts/test/` 入口执行 API、Web、Bot 与集成层测试，测试产物会统一上传。

现阶段的关键问题不是“没有测试”，而是完整回归对环境依赖较强，高风险领域也没有独立的覆盖与回归门槛。

### 4. 发布与供应链

当前已有：

- API、Web、Bot 三端镜像构建工作流。
- `amd64` / `arm64` 正式镜像。
- 版本化 Release Notes 和 Draft Release 流程。
- Docker Compose 默认镜像 tag 随版本同步。
- Git tag 签名发布能力。

当前缺口：

- 测试工作流只监听分支 push 和 PR，不监听 `v*` release tag。
- 三个镜像工作流由 tag 分别触发，不依赖同一个测试门禁。
- API、Web、Bot 分别更新版本 tag 和 `latest`，单个工作流失败时可能形成部分发布。
- 当前没有统一的镜像扫描、SBOM、镜像签名和依赖漏洞报告。

### 5. 可观测性与安全

当前主要运行期证据是应用日志、Docker healthcheck、`/health` 和部分任务状态表。对于 cron、外部调用、异步任务和补偿队列，还缺少稳定的运行指标与摘要。

当前安全基础包括：

- bcrypt 密码哈希。
- JWT 密码签名失效与强制改密闭环。
- Turnstile 登录保护。
- Internal API Secret、Webhook Secret 和敏感配置加密。
- 容器非 root 与数据库端口回环绑定。

需要继续评估和收口：

- JWT 保存于浏览器 `localStorage` 的暴露面。
- 内置 Nginx 缺少 CSP 等更严格的浏览器安全策略。
- 登录和通用 API 缺少统一限流边界。
- 依赖、容器镜像和发布产物缺少自动安全扫描。

### 6. 开源协作与文档状态

当前仓库已经具备 README、架构文档、参考文档、runbook、Issue 模板和 PR 模板，但尚缺：

- `CONTRIBUTING.md`
- `SECURITY.md`
- `CODE_OF_CONDUCT.md`
- 对外 OpenAPI / Swagger
- 明确的版本兼容矩阵和社区支持入口

2026-08-30 计划盘点已确认 `manual-search`、`manual-dispatch`、MoviePilot 通用搜索/下发、前端交互和稳定文档均已落地；对应方案已归档到 `docs/archive/plan/media-subscription/subscription-manual-moviepilot-dispatch.md`，不再按未完成新功能排序。

## 提案内容

### 1. 核心原则

- **先可信，再扩展**：发布、测试和状态可观测性没有收口前，不继续大规模横向增加高风险功能。
- **按风险治理，不按行数治理**：大文件只是入口，拆分必须围绕状态流转、外部副作用和领域边界。
- **保留当前部署形态**：不引入更多独立服务，不把内部重构变成运维复杂度升级。
- **关键链路优先**：注册、用户状态、支付、Policy 同步、订阅、MoviePilot、异步补偿优先于低风险页面和工具函数。
- **文档必须退场**：计划落地后必须提炼稳定事实并归档，不能长期停留在草稿状态。
- **用户行为默认不变**：除非具体计划明确改变产品行为，否则治理阶段只改善内部可信度和维护性。

### 2. 问题优先级

| 优先级 | 工作流 | 主要原因 |
| --- | --- | --- |
| P1 | 发布可信度与供应链 | 当前 tag 构建未与测试形成统一门禁，三端镜像存在部分发布风险 |
| P1 | 核心模块复杂度收口 | 多个核心文件已超过 1600 行，继续增长会直接提高关键链路回归概率 |
| P1 | 集成测试与高风险回归 | 测试体系已建立，但本地完整回归成本高，高风险领域缺少独立门槛 |
| P1 | 运行期可观测性 | cron、外部调用和异步补偿主要依赖日志，不利于快速判断状态是否正确 |
| P2 | 安全与发布供应链补强 | 当前基础安全可用，但缺少 CSP、统一限流、扫描、SBOM 和镜像签名 |
| P2 | 产品定位与开源入口 | 实际能力超过当前定位，但外部用户理解、接入和参与成本较高 |
| P2 | 计划文档状态收口 | 已实现方案仍留在草稿区，会持续削弱文档真相可信度 |
| P3 | 国际化与多服务器扩展 | 可能扩大用户面，但会显著增加模型、测试和维护成本，需要单独论证 |

### 3. 分阶段推进

#### 第一阶段：发布可信度和文档真相收口

目标是先消除“代码正确但发布链路不原子”的风险。

- 建立单一 release orchestration，统一执行测试、三端镜像构建、扫描和 Release 创建。
- 测试失败时禁止推送正式版本镜像和更新 `latest`。
- 三端镜像全部构建成功后再统一完成版本发布。
- 保留现有预览镜像入口，不影响 `pre_release` 使用方式。
- 正式迁移已完成正文收口的计划，并同步 plan/archive/proposals 索引与直接引用。
- 补 `SECURITY.md` 和最小贡献说明，明确漏洞报告和协作入口。

进入实施前创建：

```text
docs/plan/architecture/release-integrity-and-supply-chain.md
```

创建条件：发布工作流目标、tag 行为、`latest` 更新语义、失败回滚边界和验证方式已经明确。

#### 第二阶段：核心复杂度和回归可信度收口

目标是降低最常修改领域的认知和回归成本。

- 先对复杂度热点补特征测试，锁住当前行为。
- 按职责拆分配置定义、配置读取、连接测试和兼容迁移逻辑。
- 按订阅状态流转、MoviePilot 编排、通知副作用和查询视图拆分订阅服务。
- 按页面数据源、扫描状态、候选操作和展示组件拆分 `MediaGapsView.vue`。
- 按命令域和回调域拆分 Telegram handler，保留统一注册与装配入口。
- 为注册、用户状态、支付 webhook、Policy 同步、订阅和异步补偿建立最小高风险回归集合。
- 提供低成本的本地集成数据库准备和清理入口，但不自动启动项目服务。

进入实施前创建：

```text
docs/plan/architecture/core-module-complexity-reduction.md
docs/plan/architecture/critical-path-regression-hardening.md
```

创建条件：已确定首批文件、拆分边界、禁止改变的行为和对应测试集合。

#### 第三阶段：运行期可观测性与安全基线

目标是让管理员能够回答“系统现在是否正常”，而不必先搜索整份日志。

- 为 cron、外部集成、异步任务和补偿队列定义最小运行指标。
- 为关键任务保留最近成功时间、最近失败原因、处理数量和积压数量。
- 评估 Prometheus metrics 与管理端运行摘要的职责边界，避免重复造监控系统。
- 收口登录和通用 API 限流策略。
- 评估 JWT 存储策略和 CSP 上线兼容性。
- 增加依赖扫描、容器扫描、SBOM 和镜像签名。

进入实施前创建：

```text
docs/plan/architecture/observability-and-security-baseline.md
```

创建条件：指标消费者、暴露方式、敏感信息边界和部署兼容性已经明确。

#### 第四阶段：产品定位与开源可参与性

目标是把现有能力转化为外部用户能理解、部署和参与的产品价值。

- 将 Ember 的主定位收口为“Emby 用户运营与媒体管理平台”。
- README 增加典型使用场景、与邀请/求片工具的边界说明、截图和三分钟部署路径。
- 提供兼容版本矩阵，明确 Emby Server、Playback Reporting、MoviePilot 和 PostgreSQL 支持范围。
- 评估对外 OpenAPI / Swagger，至少覆盖稳定的管理 API 和用户 API。
- 增加 `CONTRIBUTING.md`、社区支持入口和问题复现模板。
- 国际化、多 Emby 实例和更多媒体服务器支持单独立项，不作为本阶段默认目标。

该阶段以 README、reference 和协作文档修改为主；只有涉及 API 或数据模型时才创建新的 `docs/plan/`。

### 4. 现有功能计划排序建议

现有功能实施稿继续保持独立，不并入架构治理计划。建议顺序：

1. `access-auth/registration-user-capacity.md`
   - 成本相对低，能直接解决中小型 Emby 服容量控制问题。
2. `console-admin/in-app-notification-center.md`
   - 先建立站内事件承载层，避免通知继续只依赖 Telegram。
3. `bot-telegram/notification-mute-rules.md`
   - 应复用统一通知事件类型，不单独再造一套分散规则。
4. `console-admin/device-risk-automation.md`
   - 依赖更好的任务状态、审计和通知基础，放在可观测性之后更稳妥。
5. `media-subscription/media-dedupe-and-quality-governance.md`
   - 有运营价值，但不应先于发布、测试和核心复杂度治理。

`subscription-manual-moviepilot-dispatch.md` 已完成状态复核、正文收口和正式归档，不再参与未完成功能排序。

## 风险与约束

- **治理周期挤压功能开发**：每个阶段只选择少量可验证目标，不进行无限期“基础设施先行”。
- **大文件拆分改变行为**：先补特征测试，按调用面逐步迁移，不同时修改业务语义。
- **发布工作流改造导致无法发版**：保留现有手工发布 runbook 作为短期应急路径，并写清删除条件。
- **可观测性泄露敏感信息**：指标和状态摘要只记录标识、数量、阶段和脱敏错误，不记录 Token、密码、验证码和完整外部响应。
- **安全策略破坏现有部署**：CSP、Cookie、代理头和限流调整必须先核对当前同域部署和外部反代边界。
- **文档继续漂移**：每个实施计划必须包含落地后稳定文档同步和归档条件。
- **兼容性要求**：现有 Docker Compose 部署、API 字段、用户状态流转和 Emby / MoviePilot / Stripe / Telegram 合同默认保持不变。

## 影响范围

- 文档：新增本总纲；后续按阶段新增 `docs/plan/architecture/` 实施稿，并同步 reference、runbook、README 和架构文档。
- 流程：影响测试门禁、发版、镜像构建、计划归档和开源协作流程。
- API / Web / Bot：本提案本身不改代码；具体阶段实施时按计划确定影响范围。
- 数据库：本提案本身不改 schema；后续可观测性若需要状态表，必须单独提供 migration。
- 部署：目标是保持现有 Compose 使用方式，内部增强发布和观测能力。
- 兼容性：不得以治理为由破坏现有 API、状态机和外部集成行为。

## 完成标准

- release tag 只能在统一测试门禁通过后产生正式镜像和 `latest` 更新。
- API、Web、Bot 三端正式发布具备统一成功或失败结论，不再形成部分发布。
- 首批复杂度热点完成职责拆分，关键调用面迁移完成，测试和构建通过。
- 注册、用户状态、支付、Policy、订阅和异步补偿具备明确的最小回归集合。
- 管理员能够查看关键 cron、外部集成和异步任务的最近运行状态与失败摘要。
- 基础依赖扫描、镜像扫描、SBOM 或等价供应链证据进入 CI。
- README 能准确表达 Ember 的差异化、部署方式和兼容范围。
- 开源协作与安全报告入口完整。
- 已落地的计划文档完成稳定事实提炼并退出 `docs/plan/`。
- 新增治理机制都有明确维护责任，不留下无人使用的僵尸流程。
