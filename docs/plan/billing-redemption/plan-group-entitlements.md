# 套餐与分组权益改版计划

> 状态：代码、本地 mock 与专用 PostgreSQL 针对性验证已完成；待交付收尾，尚未归档
> 负责人：Ember
> 更新时间：2026-10-04
> 口径来源：本轮用户确认的套餐、分组、永久权益与到期回退讨论。本文记录目标设计，不代表当前实现。

## 背景

当前套餐按用户所属分组限制展示和购买，支付主要延长一个用户到期时间。该结构无法同时表达“基础组永久有效、全资源组限时有效”，也无法在高级权益到期后恢复仍有效的低等级权益。

本次改为统一售卖套餐，由套餐发放分组权益。复用现有分组的媒体库与权限模板，根据用户实际持有的有效权益计算当前生效分组。

## 目标与非目标

目标：

1. 所有用户看到相同的在售套餐与定价；购买资格可以因已持有权益而不同。
2. 套餐可发放一项或多项分组权益，每项独立配置限时天数或永久。
3. 用户可同时持有多个分组权益，仅最高等级的有效分组生效；到期自动回退，无有效权益才停用资源访问。
4. 接通支付、注册、兑换、后台人工操作、到期任务及全部权限消费者，保留账号停用和管理员边界。
5. 迁移存量分组、套餐、用户与订单，提供关键流转测试及同步失败处理。

非目标：

- 不做用户手动切组、剩余价值折算、跨组时间转换、暂停计时或权益排队。
- 不做互不包含资源组的权限合并；同一时刻使用一个分组的完整模板。
- 不要求运营者提供永久套餐，不内置 A/B/C/D 套餐或固定基础/增强两层。
- 不新增自动退款体系；已付款但无法增加权益等特殊订单进入已确认的人工处理流程，不得静默吞款。
- 已获用户授权按本计划实施，遇到未决业务问题先暂停询问；不包含提交、部署、启动服务或真实外部调用授权。

## 已确认的业务规则

### 术语与职责

| 概念 | 职责 |
| --- | --- |
| 权益分组 | 复用 `PlanGroup`，定义完整资源/权限模板和独立权益等级；资源范围逐级包含 |
| 付费套餐 | 售卖商品，定义价格及发放的权益明细，不再定义哪些当前分组可以买 |
| 用户持有权益 | 用户对某分组的授权，具有明确的永久或限时状态，并可追溯来源 |
| 当前生效分组 | 最近一次权益变更或到期任务重算后选出的最高等级有效分组；到期自然流逝不要求立即切换 |
| 回退权益 | 用户实际持有且仍有效的低等级权益，不是系统默认组或上一次所在组 |

### 售卖与发放

- 展示所有启用在售套餐；下架不撤销已发放权益。完全不能增加权益的购买显示“已拥有”并由服务端拦截。
- 同组限时续费：未过期从原到期时间追加，已过期从支付履约时追加；重复回调不重新起算。
- 同组永久授权不被限时授权覆盖；购买永久后不折算、退还原限时剩余价值。
- 跨组独立计时，不相加、不暂停、不相互清除。买低等级权益不强制替换仍有效的高等级权益。
- 组合套餐分别发放各项权益，明确每项期限；部分权益已拥有时展示重叠项，首版不抵扣价格。完全无增益才禁止购买，跨等级永久覆盖的判定见下方补充确认。
- 只在支付成功履约时发放；创建订单、取消支付、失败支付不能改变权益。
- 新模型取代讨论早期“跨组覆盖并丢弃旧权益”的 B 方案，该早期方案不再适用。

永久高等级覆盖规则补充确认（2026-10-04，用户确认实施澄清第 3 类推荐规则）：

- 已持有高等级永久权益时，即使没有单独持有低等级权益，购买同级或低等级权益也判定为无新增权益并禁止购买。
- 高等级权益仅限时有效时，不据此禁止购买低等级永久权益，后者可作为到期后的保底。
- 组合套餐逐项判断，已被永久权益覆盖的项目不计为新增权益；全部无增益才禁止购买，部分重叠沿用展示已有项且不抵扣价格的规则。
- 该判定依赖已确认的逐级包含分组模型；115 等配置按生效分组整体应用，不合并，也不按属性数值重新判定分组等级。

### 典型场景

以下 A/B/C/D 仅为示例：A 发基础组永久，B 发全资源组 30 天，C 发全资源组 180 天，D 发基础组永久和全资源组永久。实际套餐填写明确天数，不把“半年”隐式解释为自然月。

| 场景 | 结果 |
| --- | --- |
| A → B | 30 天使用全资源组，到期回基础组永久 |
| 基础组剩 60 天 → B | 30 天后回基础组，基础剩约 30 天 |
| 基础组剩 10 天 → B | B 到期时基础也已过期，停止资源访问 |
| B → C | 同一全资源组期限追加 180 天 |
| A 或 B → D | 对应权益变永久，持续生效全资源组 |
| D → A/B/C | 没有新增权益，禁止购买 |
| 不配置 A、D，只售 B/C | 限时权益照常续期，到期无其他有效权益则停用 |
| 不配置 A，只售 B/C/D | 只买 B/C 没有保底；D 可独立发放两项永久权益 |
| 不配置 D，只售 A/B/C | 买过 A 才有永久保底 |
| 买过 A 后 A 下架 | 用户已持有的永久权益保持 |

### 兑换码补充确认（2026-10-04）

来源：用户在实施澄清第 1 问确认“可以按你的来”，并明确历史兑换码全部按过期处理。

- 新兑换码明确绑定目标权益分组，兑换时只延长该组权益，不延长其他当前生效组。
- 已持有目标组永久权益时拒绝兑换，不消耗次数、不生成成功兑换记录。
- 历史兑换码在升级时统一失效，注册与续期两个入口均不得继续使用；不推断旧注册分组的续期含义。
- 保留历史兑换记录、使用次数和已发放给用户的权益，不因旧码失效撤销既有授权。
- 迁移仅作用于切换前的旧码，幂等重跑不得误伤新规则下创建的码；具体迁移机制随 schema 方案确定。
- 注册发放规则于后续确认，见下节；续期与注册复用同一目标分组语义。

### 注册发放补充确认（2026-10-04）

来源：用户确认沿用现有注册权益来源，并询问 0 天试用是否已有支持。

- 开放注册且 `default_trial_days > 0`：发放注册时默认分组的对应天数权益；后续修改默认分组不改变既有授权归属。
- 开放注册且试用天数为 0：创建账号但不赠送资源权益，允许登录购买；新模型显式表达无权益，不把空期限当永久。
- 使用新兑换码注册：按码绑定的分组和天数发放，不额外叠加默认试用权益。
- 当前配置 `default_trial_days` 已支持最小值 0；注册在试用天数不大于 0 时请求创建初始禁用的 Emby 账号，已有 fake 测试覆盖。此项是将现有行为接入新权益模型，不新增试用开关。

### 生效、到期与封禁

后台人工权益管理补充确认（2026-10-04，用户确认管理权益，并要求保留手动延长有效期）：

- 管理员按目标分组新增、调整或撤销用户权益，由系统重新计算当前生效分组。
- 保留到期时间管理：可对某一分组权益追加天数、修改到期时间或设为永久；其他分组权益不受影响。
- 例如用户持有 A 永久和 B 限时，管理员给 B 延长有效期只更新 B；B/C 套餐若都发放同一分组，调整的是该分组聚合权益，不改写历史订单或套餐商品配置。
- 账号停用保持独立，不删除已购买权益；人工调整记录操作人、目标分组及调整前后期限。

权益重算时按该次业务时间过滤权益，选择最高等级有效分组；限时权益在 `expiresAt <= now` 时不参与选择。使用独立唯一等级避免同级歧义，不能按展示排序或购买先后决胜。到期时间和实际执行回退的时间允许不同，具体见下方调度确认。

有有效低等级权益时仅回退，使用它原来的期限；无有效权益时停止资源访问，但允许未被停用的 Ember 账号登录续费。账号 `isActive`、人工 `embyAccessDisabled` 与权益有效性是不同维度，重算、续费和回退均不能解除人工封禁。管理员绑定 Emby 的既有非普通用户策略必须保留。

到期调度补充确认（2026-10-04，用户明确要求简化处理）：

- 用户说明当前部署已配置每天多个时点检查；沿用现有 `CRON_SCHEDULE`、`CRON_ENABLED` 和 `CRON_TIMEZONE`，不改检查频率或开关归属。代码读取可配置 cron 表达式；仓库默认值不代表实际部署值，本轮未读取部署数据库。
- 允许到期后等待下一次既有定时任务再回退分组或停用。撤销此前每分钟到期检查、请求时实时重算、独立于总开关运行及新增启动补查的建议，不新增到期兜底机制。
- 到期任务执行时必须重读最新权益，正确区分继续有效、回退和无权益停用；重复执行幂等，不能以过时扫描结果覆盖并发续期。
- 支付、兑换和管理员主动调整仍在对应业务操作中更新权益与当前分组；自然到期只按定时任务处理，不给各消费者新增请求时自动回退逻辑。
- 本地消费者使用统一生效结果，避免旧单日期判断把“等待任务回退且存在保底”误判为无权益。沿用必要的既有 Policy 同步失败记录与人工重试，不增加额外补偿系统；不承诺远端即时缩权或立即中断播放。

115 与其他分组限制补充确认（2026-10-04，用户明确“哪个分组生效，就按哪个生效的分组来进行限制”）：

- 115 账号来源模式、并发限制、转存配额及求片额度继续属于分组配置；统一使用当前生效分组的完整配置。
- 从 B 回退 A 时全部改用 A 的配置，不叠加、不取最大值，也不要求不同分组使用相同的 personal/system 模式。
- 等级决定生效组，媒体库逐级包含校验仍执行；不对非资源库属性自动调大或合并。切组只改变适用限制，不重置已统计的用量。

## 方案设计

### 1. 数据边界与迁移资产

以下为逻辑结构，具体表名、索引和 DTO 在实施阶段定稿：

| 数据 | 必需信息与约束 |
| --- | --- |
| 分组 | 独立权益等级；逐级媒体库包含关系；保留原模板，不对数字配额或 personal/system 模式做自动合并 |
| 套餐权益明细 | `planId`、`planGroup`、`validityType`（`duration/permanent`）、`durationDays`；同套餐同组不重复；限时天数为正整数，永久不填天数 |
| 用户分组权益 | `userId`、分组、明确有效期类型、到期时间；同用户同组聚合授权唯一，永久与无权益不可混淆 |
| 发放/调整记录 | 订单或注册/兑换/管理员/迁移来源，变更前后期限；来源幂等标识，支持审计且不存敏感支付响应 |
| 订单权益快照 | 购买时的分组与每项期限配置，不可变；与金额/币种共同锁定交付内容 |
| 当前权益摘要 | 最近重算后的生效分组、对应期限、是否永久、是否允许访问；由权益生成并随主动变更及到期任务更新，不独立人工写入 |

所有模型映射显式声明 `gorm:"column:..."`；数据库名称 snake_case，对外 camelCase。新增 schema 和约束必须提供 `infrastructure/database/YYYYMMDD_NN_*.sql`，明确回填、重复执行、校验与失败恢复，不依赖 `AUTO_MIGRATE`。

### 2. 统一权益服务与消费边界

权益服务负责发放、续期、管理员调整、有效性计算和当前分组解析；payment 负责支付编排，policy 负责 Emby 协议同步，handler 不承载业务规则。

`users.planGroup/expiresAt/resourceAccessGranted` 保留为生效投影，必须明确不是完整持有权益，`expiresAt` 表示当前生效项期限，不代表全部权益；“无有效权益”须有显式状态，不能用 null 日期被旧逻辑当作永久。内部发放入口已迁移到统一权益服务；旧单组 API 输入保留受限兼容，删除条件为外部调用方完成 benefits 迁移并明确发布破坏性接口版本。组合读取和修改不得通过旧摘要字段进行。

统一迁移的消费者包括：账号/Profile、用户筛选、媒体库偏好、求片准入和额度、115 路由/并发/配额、Gateway Token 门控、Bot 账号查询与续期、通知及过期任务。不得只更新支付和用户页面。

本地权限消费者使用统一的生效结果；自然到期由现有定时任务重算后更新，允许等待下次调度。不新增请求时重算、每分钟到期轮询、启动补查或独立调度开关。Emby 使用既有 Policy 同步路径，不宣称数据库到期等于远端已同步。

### 3. 接口与页面合同

- 套餐查询返回统一 `data` 列表，权益明细建议为 `benefits[{planGroup, validityType, durationDays}]`；用户态附购买资格及原因，价格和售卖目录保持一致。
- 管理端套餐保存接收权益明细；分组管理增加权益等级及包含关系校验；等级/媒体库变更需重算受影响用户并同步权限。
- 用户/Profile 与 Internal API 返回权益列表及当前摘要，明确区分 `hasAccess`、当前永久/到期和后续保底；订单详情展示快照，不根据当前套餐反推。
- 兼容字段不能静默把组合套餐压成单个 `days/planGroup`；逐一迁移 Web/Bot 调用方，列明旧 DTO 退出条件。
- 前端实现必须遵守 Ember 风格；设计与交互基线以 [前端设计规范](../../reference/web-design-guide.md) 为准，无计划内偏离。沿用计费中心、续费中心、账号中心和用户管理的页面职责，不新增平行入口。
- 套餐显示各项资源权益和 30 天/60 天/永久；组合逐项标注。用户摘要展示当前分组、期限和有效保底；“已拥有”、支付待处理、权限同步失败必须区分。

### 4. 支付、重算与同步流程

1. 创建订单：加载在售配置，在一致的用户权益视图下判定增益，写入价格与权益快照，沿用已有 Checkout 占位幂等机制。
2. 成功回调：沿用用户再订单的锁顺序、事件去重与 completed 终点；锁内根据快照原子发放全部权益、重算当前摘要、标记履约完成。不再因当前分组变化拒绝已付订单。
3. 事务提交后通过既有 Policy 同步链路应用当前完整权限；失败保留已付款权益和可重试状态，不能回滚为未付款。
4. 到期任务：查需要重算的用户，锁内读取最新权益，区分无变化、回退、彻底失效；不沿用“筛到旧日期就先撤销所有 Token”的顺序。
5. Emby 写入沿用用户级串行锁并重读最新权益；旧回退任务不能覆盖刚续费的最新权限。锁顺序、事务与网络调用边界必须通过并发测试明确。
6. 用户媒体库隐藏偏好只能缩小当前组授权范围，不得通过保留偏好恢复已到期组资源。完整使用当前组模板，不拼接多组权限。

时间规则复用唯一 `CRON_TIMEZONE`。时间戳按既有 UTC 存储约定在边界转换，用户展示和业务日期计算使用全局配置；“一天”采用自然日还是固定时长需与现有续期合同核对后定稿并补夏令时测试，不新建子系统时区。

### 5. 失败与兼容边界

异常已付款订单补充确认（2026-10-04，用户确认实施澄清第 4 类推荐方案）：

- 下单时有增益，但实际付款前因其他购买或管理员授权变为无增益的订单，保留付款成功事实，进入“待人工处理”，不标为正常履约完成。
- 升级后收到成功付款事件、但无法可靠还原购买内容的历史订单进入同一流程，不伪造权益快照。
- 后台展示原因和付款事实，由管理员核对后处理退款或补偿并记录结果；不自动调用退款。具体状态字段/API 在实施时设计，付款状态与履约/人工处理状态不得混淆。
- 重复支付回调不重复建待办、发放或通知；一旦进入人工处理，不因同一事件重投自动转为普通履约。补偿发放与人工收口也须具备幂等保护。
- 组合订单部分已覆盖但仍有新增权益时，沿用组合套餐规则发放未覆盖部分；只有整体无增益或无法确定交付内容才进入此人工流程。

- 重复/乱序回调、支付与到期并发、两个套餐并发购买、永久和限时并发发放：权益不丢失、不降级、不重复延长。
- 下单后通过另一订单获得永久权益，原订单仍可能真实付款；创建时校验不能覆盖此竞态，按上述已付款人工流程收口。
- 分组被套餐、用户权益、订单快照引用时不可直接删除导致履约或回退悬空。模板变更与套餐下架不等于撤销权益。
- 本地保存成功与远端成功分别记录。日志包含 userId、paymentId、变更原因、前后组、期限、任务与失败阶段，不输出密码、Token 或完整外部响应。
- 远端收窄权限失败有暴露旧权限的风险，须明确重试/管理员处理及 Gateway 本地拒绝边界；不得把“已入队”展示为“已同步”。

## 存量迁移与实施前待定项

### 迁移原则

1. 老套餐的单组和天数转换为一项限时权益配置；先盘点非正数天数等异常，不自动当永久。
2. 老用户根据迁移截点的有效分组与到期时间生成来源明确的权益记录；空分组需解析当时默认组并固定归属。空到期时间、管理员、未绑定、人工停用、已过期及引用缺失分别验证，保留原语义，不凭字段空值批量发永久权益。
3. 不能按历史订单再次逐笔发放，否则会和当前剩余期限重复计时；迁移来源必须幂等。
4. 既有分组未必资源逐级包含。升级保留现有用户分组、权限和有效期，由管理员显式配置权益等级；系统校验高等级媒体库范围包含低等级范围，不根据名称/展示排序推断，不自动扩大权限。配置未完成或校验不通过时暂停新套餐购买，已付款订单继续按履约或人工处理规则收口；通过后才开放新售卖。此切换规则于 2026-10-04 经用户确认（实施澄清第 5 类等级迁移问题）。
5. 老 completed 订单只补追溯兼容，不重新履约。旧 pending/failed/expired 订单可能有迟到成功事件；历史目标分组无法可靠重建时不得伪造快照，按已确认的已付款人工流程处理；切换窗口与技术识别方式在迁移方案中明确。
6. 在切换窗口统一停用旧权益写路径，完成回填校验后再开放新写路径；不得让旧版 API/worker 与新版并行写两种语义。提供升级 runbook、恢复点和回退限制，不能用旧二进制直接覆盖新数据语义。

### 实施前口径与证据收口

以下区分已确认口径和剩余事项，不重复询问已确认规则：

- 兑换码、后台人工管理和注册发放口径已确认，见相应补充确认；实施时将各入口接入统一权益服务。
- 永久高等级覆盖低等级的购买限制已确认；115 与其他限制跟随生效分组，见相应补充确认。
- 下单后变为无增益仍付款、无法重建的老订单迟到付款已确认进入待人工处理，不自动退款；见异常已付款订单补充。
- 等级映射和非逐级资源迁移已确认采用管理员配置、包含校验与新售卖门控，见迁移原则第 4 项；高等级不等同于所有配置数值更大，各组完整模板按生效结果应用。
- 到期处理已确认沿用现有调度并接受延迟，不做实时兜底；实现仍需核对现有 Token/Policy 路径，保证回退不走无权益停用分支，不扩展播放会话中断能力。
