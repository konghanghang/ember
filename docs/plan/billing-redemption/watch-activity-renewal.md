# 分组观看保号方案

> 状态：代码与本地自动化、专用 PostgreSQL、管理员配置浏览器验收完成；截至 2026-10-23 已随镜像部署，用户端浏览器、真实播放与权限同步待验收，保留计划
> 负责人：Ember
> 更新时间：2026-10-25（补充历史部署证据，保留未完成的业务验收）

## 背景

公益套餐希望让持续观看的用户长期使用，同时回收不活跃用户的访问权益。套餐负责授予分组权益，分组决定保号策略。观看保号代码已接入分组配置、独立 cron 和权益流转；默认关闭，套餐描述本身不会启用规则。

2026-10-05 用户确认以“永久权益 + 每日考核最近 30 天累计观看”取代原来的自动延期设计。2026-10-08 更新确认：分组统一配置一个考核周期 N 天（默认 30 天），观察期和滚动统计窗口共用该周期，不拆成两个天数字段。保号组 A 被正常付费组 B 替代期间暂停考核；B 到期后，从 A 实际接替生效时开始完整的 N 天观察期，不从 B 的名义到期时间起算。A 使用 10 天后再次被 B 替代，后续重新接替时仍重新获得 N 天，不接续原观察期剩余天数。此规则替换此前“购买即起算、其他组生效期间持续考核”的约定；已失效权益不会因切组自动恢复。

## 目标与非目标

目标：按分组配置观看保号；保号套餐默认授予永久权益，通过 N 天观察期和每日滚动考核维持资格；没有任何有效权益时停止 Emby 访问，保留 Ember 登录及购买入口。

非目标：观看授予新分组、观看自动恢复失效权益、解除人工封禁、叠加其他分组期限、实时考核或高频扫描。用户已于 2026-10-08 授权开始实现；按 TDD 推进代码、SQL migration 与文档，不启动项目服务，不修改线上配置，不执行真实外部验证。

## 方案设计

### 1. 分组配置与永久权益

以下规则由用户于 2026-10-05 确认：套餐授予分组权益，保号策略统一放在分组，同组套餐遵守相同策略，不按购买来源叠加多套保号配置。

| 配置 | 规则 |
| --- | --- |
| 观看保号开关 | 按分组设置，沿用默认关闭的兼容边界 |
| 考核周期天数 | 按分组配置为 N 天，默认 30 天；同时决定接替后的观察期和每日考核的回看窗口，不分别配置；范围 1..3650 天 |
| 最低有效观看分钟数 | 最近 N 天累计门槛，允许分多天完成；开启保号时须明确填写 1..5256000 的正整数；未配置时表单留空，关闭时空值提交为 `0`，已有正数在切换开关时保留 |

分组只提供上述三项保号配置。观察期和滚动统计窗口共用“考核周期天数”，不写死为 30 天，也不另设观察天数或统计窗口天数。该周期不是续期天数。保号套餐默认永久，表示没有固定到期日，但不代表无条件保留权益。观看达标不修改到期日，不累加天数，也不重置观察期。

### 2. 观察期与每日考核

2026-10-18 用户确认：开启或修改分组规则不重置权益原起点。每日调度按每条权益本轮实际生效／接替时间判断是否已满 N 天；这不是用户注册时间，也不是分组开启时间。该补充替换旧实现中的配置重开规则，保留实际接替、明确恢复时重新起算。

- 保号组实际成为当前生效组时，开始完整的 N 天观察期，与注册时间无关。购买后尚由更高等级正常付费组提供权益时，不提前消耗该观察期。
- 正常付费组 B 生效期间，保号组 A 暂停考核。B 到期后，仍有效的 A 实际接替时重新开始 N 天观察期；起点不回填为 B 的名义到期时间，避免定时任务处理延迟缩短观察期。
- A 被 B 替代后暂停考核，再次实际接替时重新获得完整 N 天，不续接原观察期剩余天数，也不沿用首次购买时间。例如配置 N=30，A 使用 10 天后切换到 B，再回到 A 时重新获得 30 天，不接着算剩余 20 天。
- 当前检查时间距离本轮观察期开始不足 N 天时，跳过对应权益的保号考核；满 N 天后参与每日检查。
- 每天按最近 N 天累计有效观看分钟数判断，累计值大于或等于分组门槛即达标，低于门槛则对应权益失效。统计不能仅限于检查当天，也不是按固定月周期清零；观看达标不重置观察期。
- 重新购买或管理员明确恢复已失效的权益后，若该组实际生效，开始完整 N 天观察期；若仍由正常付费组生效，则等待该保号组实际接替。普通切组不能恢复已经失效的权益。
- 购买其他分组但未改变当前生效组，不构成重新开始观察期的理由。重复支付回调、重复重算同一生效组和任务重试不得重置起点；只有实际接替或明确恢复等有效事件可以开启新观察期。
- 有效观看仍按用户累计，不将分钟数在组之间分摊或消耗；正常付费组生效期间不执行 A 的保号考核。实施统一只考核当前生效组，其他组等待实际接替；任何有效保号组实际接替时重开周期，不恢复已失效组。
- 2026-10-08 用户确认：N 天按全局业务时区的日历日计算，保留接替时刻；满 N 天后参加下一次考核，统计窗口为实际执行时刻向前 N 个日历日的半开区间。考核 cron 表达式必须可配置，默认 `0 2 * * *`，首次检查日期按实际表达式求得，不写死凌晨 2 点。
- 调度、日期边界和外部本地时间解析统一使用 `CRON_TIMEZONE`；实际接替以本地权益投影事务为起点，N 天采用全局时区日历日，首次考核按进程实际注册的 cron 计算。本地权益切换与远端权限同步成功必须分别记录，不得用未证实的远端成功时间代替起点。

### 3. 失效与恢复

- 不达标使对应保号权益失效，不能只修改 Emby 登录开关而保留一条仍被认定有效的永久权益。
- 失效后不能因后来观看达标、普通权益重算或 Policy 同步自动恢复；必须重新购买相应分组的套餐，或由管理员明确恢复该权益。
- 购买其他分组的套餐只授予相应权益，不恢复原来失效的保号权益。
- 某组失效但仍有其他有效组时，按已有等级规则选择生效组并同步资源权限；只有全部权益不可用时才禁用 Emby，始终保留未被人工停用的 Ember 账号登录及购买入口。
- 保号失效独立于人工账号停用或 Emby 人工禁用；购买或保号权益恢复不得绕过独立的人工限制。
- 失效历史和原因应保留供排障，不能通过删除用户或清空历史实现失效。

### 4. 模块与数据边界

- 分组管理 API/Web：维护三项保号配置：开关、考核周期天数、最低有效观看分钟数。前端实现必须遵守 Ember 风格，设计与交互以[前端设计规范](../../reference/web-design-guide.md)为准，本计划不引入偏离规范的特例。
- 播放适配层：基于核实的版本化合同提供可追溯的有效观看事实、统计窗口及数据完整性结果，不直接修改权益。
- 权益服务：统一处理观察期、保号资格失效、购买重获和管理员恢复，将资格纳入有效分组选择，处理实际接替起算、被替代期间暂停考核、再次接替重开观察期，以及购买、恢复、换组、到期任务与保号任务的并发。
- 调度层：每日执行保号考核，复用权益重算和现有 Emby 同步职责；与自然到期任务的顺序及幂等边界在技术设计中确定，不增加请求时考核。
- 数据库：分组保存上述三项公共规则；用户持有权益（`UserEntitlement`）记录各自的本轮观察期起点和保号失效状态，不重复配置周期天数或分钟门槛。考核证据保留当时使用的规则与结果，供审计追溯。已落地 `watchRetentionStartedAt/watchRetentionInvalidatedAt` 两个权益状态字段，分组内部重开字段已通过 `20261018_01_remove_watch_retention_reset.sql` 删除，考核与页面共用权益起点，审计保存于 `watch_retention_checks`。模型、索引或约束变化必须同步幂等 SQL migration，不能依赖 `AUTO_MIGRATE`。
- 所有有效权益消费者都必须识别保号失效，避免永久到期日使失效权益重新参与分组选择。Emby 同步沿用现有访问投影与人工限制边界，不能另建互相覆盖的账号开关。
- 对外字段使用 camelCase，列表使用 `data`，GORM 显式映射列名。DTO、SQL 与调用方已同步，详见 API 目录及运行手册。

### 5. 关键流程与失败处理

1. 读取开启保号的分组及对应有效权益，排除由正常付费组替代而暂停考核、尚未实际生效及仍处于观察期的权益；已失效权益不通过扫描自动恢复。
2. 通过已核实的数据源统计最近 N 天有效观看，校验数据完整性后与门槛比较。
3. 达标则保持权益；不足时，在权益写入边界重读分组配置、当前生效组、本轮观察期起点及当前资格，避免旧扫描覆盖并发切组、购买或人工恢复。
4. 保存统计证据、失效原因和处理结果，统一重算有效组，按既有链路同步 Emby 访问策略。

失败处理约束：播放数据缺失、协议无法确认、外部查询失败或结果被截断时，不得将未知结果当作零观看并批量失效；跳过受影响考核并记录失败原因。完整且有效的零观看结果才可用于判定不足。重试不能重复失效或重置观察期，远端同步失败不能被描述为已成功禁用。日志保留用户/分组标识、统计窗口、门槛、累计时长和失败点，不记录凭据或完整外部响应。

### 6. 用户侧观看要求展示（2026-10-08 已实现）

- 概览的“服务状态”卡片只展示当前生效权益组的观看要求；该组未开启观看保号时不显示。当前使用普通付费组 B 时，不在概览展示保底组 A 的要求；A 实际接替后再展示。
- 账号中心的持有权益按每条权益所属分组分别判断；开启观看保号的展示观看要求，包括尚未生效或被正常付费组替代的保底权益；未开启的完全不显示相关提示，不增加“无需观看”等占位文案。
- 展示依据是分组开关和配置，不根据商品描述、套餐名称或“永久”字样猜测。周期 N 和最低分钟数 M 读取对应分组配置，不写死示例值。
- 面向用户只写一条“观看要求”，不使用“观察期”术语或额外叠加相关状态标签。遵守 Ember 风格和前端设计规范的文案克制规则，不扩展观看进度、菜单或新页面。

| 适用情况 | 提示模板 |
| --- | --- |
| 当前已生效，尚未到本轮首次检查 | 观看要求：最近 N 天累计观看至少 M 分钟，首次检查为 D。 |
| 当前已生效，已进入每日检查 | 观看要求：最近 N 天累计观看至少 M 分钟，每天检查。 |
| 尚未生效，或被正常付费组替代而暂停考核的有效权益（仅账号中心） | 观看要求：生效满 N 天后，每天检查最近 N 天是否累计观看至少 M 分钟。 |

示例：N=30、M=60、D 为 11 月 8 日时，首条显示“观看要求：最近 30 天累计观看至少 60 分钟，首次检查为 11 月 8 日。”示例值不代表默认分钟门槛或固定检查日期。

首次检查日期以本轮实际接替起点、配置周期和每日考核安排为准，统一使用 `CRON_TIMEZONE` 展示，不直接用 B 的到期时间推算；再次接替时同步更新。API 应提供展示所需的规则和考核阶段/日期事实，`watchRetention` DTO 提供规则、阶段和可选首次日期，前端不独立猜测日期或资格。已失效权益显示原观看要求和失效状态，不套用“生效满 N 天后”暗示自动恢复；cron 关闭时仅保留要求，不显示检查日期或“每天检查”。

## 实施边界与剩余验收

1. 用户确认 Emby 4.9.3.0 / Playback Reporting 2.1.0.7 版本一致，并接受按记录开始时间选窗口、电影/剧集累计播放减暂停、多设备相加；不逐秒拆分跨窗口或去除设备重叠。固定协议和响应故障由 mock 合同测试锁定。
2. 实际接替时间在用户权益事务内写入，普通续期保留起点；购买或管理员明确恢复已失效权益清除失效标记，实际生效时重新起算。重复回调保持幂等；普通管理员换组保留原失效状态。
3. N 天按全局业务时区日历日计算。`WATCH_RETENTION_SCHEDULE` 默认 `0 2 * * *`，设置中心可配置、重启生效；实际考核与用户首次日期共用日历 cron 校验，拒绝表达式自带时区及 `@every`。已有不支持的配置暂停保号，修正后重启恢复；暂停时权益仍可读取且不显示检查日期。
4. 只考核当前生效权益；限时权益仍保留原到期日和自然到期机制，不因保号达标延期。其他权益在接替时重开周期。
5. 首次开启、重新开启或修改周期/门槛均保留原权益起点；修改周期按原起点和新 N 重算首次日期，修改门槛不改变日期，未生效者等接替。关闭开关停止考核，不恢复此前失效权益。起点缺失时记录原因并跳过，不推算或自动回填。周期范围 1..3650 天、默认 30 天；最低分钟数开启时由管理员明确填写，范围 1..5256000。
6. SQL 错误、列缺失、非法数值、超限或不完整响应均跳过考核，保存阶段化日志；查询期间身份、分组、期限、起点或配置发生变化时丢弃旧结果。已经丢失或被插件清理的历史不能靠成功查询识别，部署必须保证采集与保留范围，见运行手册。
7. 专用 PostgreSQL 生命周期测试及六项相关回归已于 2026-10-08 补跑通过；2026-10-11 管理员分组与无效 cron 浏览器复验通过。2026-10-23 已有镜像部署记录；用户端展示、真实播放与保号失效后的权限同步仍未验收，保留计划。
8. 2026-10-11 已补齐事务内 Policy 同步任务：本地失效与待同步意图一起提交，提交后即时消费，中断由既有 worker 恢复；替换活跃任务使用新 ID、保留批次，旧任务完成不能关闭新变更。同步失败继续保留 failed 供管理员重试。
9. 扫描使用独立的每用户尝试进度，先处理从未尝试及最久未尝试的用户；失败和中断也推进顺序，不伪造观看证据。`20261011_01_watch_retention_scan_progress.sql` 无回填且可重复执行；10 分钟预算结束后下一轮继续覆盖未触达者。

## 验证方式

实现及修复均按先失败后通过的回归测试推进；Go 外部依赖全部 mock，数据库专项使用专用 PostgreSQL 隔离 schema，前端测试不依赖真实后端，Bot 同样 mock 外网与 Internal API。

| 场景 | 验收预期 |
| --- | --- |
| 开关关闭、无目标组权益 | 不参与保号失效，不授予新组 |
| 配置非默认周期，例如 N=14 | 实际接替后观察 14 天，满期后每天统计最近 14 天，不残留固定 30 天逻辑 |
| 开启保号但周期或分钟门槛非正整数 | 拒绝保存，不产生部分配置写入 |
| 新建或编辑零门槛分组后开启保号 | 分钟数保持空白，未明确填写时不发送保存请求；关闭时空值按 `0` 提交 |
| 设置中心保存无效 cron 返回 `400` | 展示服务端错误、保留草稿并恢复按钮，不产生未处理异常；修正后可重试 |
| 注册或购买已满 N 天，但 A 实际接替不足 N 天 | 按本轮实际接替起点跳过考核 |
| 观察期不足 N 天、恰好满 N 天 | 分别跳过、参与考核；按收口后的时间边界测试 |
| 多天多段观看累计恰好达到门槛 | 保留权益，不更新永久期限或观察期起点 |
| 窗口滑动后累计不足 | 对应保号权益失效，保存原因 |
| 暂停、拖动、跨窗口、多设备、重复记录 | 按核实合同统计，不虚增有效观看 |
| 权益失效后有新观看、普通重算或 Policy 同步 | 不自动恢复失效权益 |
| 重新购买同组套餐、管理员明确恢复 | 恢复对应权益；实际生效时开始 N 天，仍由 B 生效时等待接替 |
| 购买其他组套餐 | 只授予对应组，不恢复或重置原失效组 |
| 重复支付回调、任务重试 | 不重复发放、重置观察期或失效 |
| 多组共存、某个保号组失效 | 选择最高有效组，保留其他权益期限及观察期 |
| 正常付费组 B 生效期间无观看 | A 暂停考核，不因这一期间无观看提前失效 |
| B 名义到期后，定时任务延迟才使 A 接替 | 从 A 实际接替起算完整 N 天，不回填 B 到期时间 |
| N=30，A 使用 10 天后切到 B，之后再次切回 A | A 重新获得完整 30 天，不续接剩余 20 天 |
| 重复回调、重复重算同一生效组、任务重试 | 不重置本轮观察期 |
| A 考核扫描期间切换到 B 或重新接替 A | 旧考核不能使暂停考核或新观察期中的 A 失效 |
| 多个保号组切换 | 只考核当前生效组，其他有效组实际接替时重开周期，不恢复失效组 |
| 正常组到期，公益组分别处于有效/失效状态 | 前者回退公益组；后者不恢复公益组，无其他有效权益时禁用 Emby |
| 所有组失效 | 禁用 Emby，保留 Ember 登录和购买入口 |
| 人工停用或人工 Emby 禁用 | 购买和保号恢复不绕过独立人工限制 |
| 扫描与购买/恢复/换组/自然到期并发 | 旧结果不能覆盖新权益或观察期 |
| 查询失败、数据缺失/截断与完整零观看 | 前者跳过并记录；后者按门槛判断 |
| Emby 同步失败 | 本地资格与远端同步结果分别可追溯，不报告虚假成功 |
| 失效提交后、即时 Policy 同步前退出 | 已持久化任务可在新 worker 中完成禁用或降组 |
| 原 Policy 任务仍在处理时发生保号失效 | 新意图换新任务 ID，保留批次，旧任务完成不覆盖新任务 |
| 考核成功/失败前缀后取消，再创建 worker | 优先处理尚未触达用户，不将未知观看结果记为零 |
| 配置 `@every` 或升级前已有该值 | 保存拒绝；已有值暂停考核，权益仍可读且不展示虚构日期 |
| 当前组未开启保号、保底组开启 | 概览不显示观看要求，账号中心仅保底权益显示要求 |
| 各权益保号开关不同 | 逐条按所属分组决定显示，未开启者无提示或占位 |
| 首次检查前、每日检查中、尚未生效/被替代 | 使用对应模板，不展示“观察期”术语；N/M 取实际配置 |
| 非默认周期及跨业务日期、再次接替 | 两处提示使用一致的配置，首次检查日期符合实际调度及全局时区，重新接替后更新 |
| 已失效权益 | 不显示暗示自动恢复或已进入每日检查的提示 |
| 配置变更、存量迁移、晚到数据 | 按实施前收口的规则验证，不凭旧期限推断资格 |

实现阶段在 `services/api` 执行适用的 `go test`、`go vet ./...`、`go build ./...`；在 `services/web` 执行相应测试及 `npm run build`。按影响面补 mock 合同测试、数据库并发与迁移测试。真实 Emby 验收另行授权，不能将 mock 通过表述为外部链路已验证。
