# 分组观看保号方案

> 状态：核心业务规则已确认，播放合同与技术边界待核对；仅保存计划，暂缓实施
> 负责人：Ember
> 更新时间：2026-10-05

## 背景

公益套餐希望让持续观看的用户长期使用，同时回收不活跃用户的访问权益。套餐负责授予分组权益，分组决定保号策略。当前观看保号尚未实现，套餐描述中的相关文案不会触发自动处理。

2026-10-05 用户确认以“永久权益 + 每日考核最近 30 天累计观看”取代原来的“单日观看达标后延长到期时间”。观察期从购买或人工恢复开始，不按注册时间计算；不达标使对应权益失效，重新购买或管理员恢复后重新开始观察期。本计划已统一替换旧延期设计。

## 目标与非目标

目标：按分组配置观看保号；保号套餐默认授予永久权益，通过 30 天观察期和每日滚动考核维持资格；没有任何有效权益时停止 Emby 访问，保留 Ember 登录及购买入口。

非目标：观看授予新分组、观看自动恢复失效权益、解除人工封禁、叠加其他分组期限、实时考核或高频扫描。本轮不修改代码、数据库或线上配置，不执行外部验证。

## 当前事实

- 前置方案：[套餐与分组权益改版](./plan-group-entitlements.md)；现行边界见[系统架构](../../system-architecture.md)。
- 商品通过 `Plan.planGroup/validityType/days` 发放单组权益，订单保留权益快照；用户可持有多条 `UserEntitlement`，各组独立计时，最高有效权益等级决定生效组。
- `User.planGroup/expiresAt/resourceAccessGranted` 是访问投影；分组同时决定资源库与相应限制。高等级组到期后可回退到仍有效的低等级组。
- `services/api/internal/services/entitlement/` 负责权益计算与持久化；`services/api/internal/services/system/expiry.go` 负责既有定时到期处理。观看保号尚未实现，不能仅将期限设为永久就视为功能已生效。
- Emby Server 目标版本为 4.9.3.0；现有[播放合同](../../reference/playback-reporting-api-contract.md)核对了 Playback Reporting 2.1.0.7 固定源码，实际安装插件版本未确认。插件记录播放开始时间及累计播放/暂停时长，没有逐段暂停区间或历史版本；能否完整满足保号统计仍未证实，不能直接将排行榜聚合值作为授权依据。

## 方案设计

### 1. 分组配置与永久权益

以下规则由用户于 2026-10-05 确认：套餐授予分组权益，保号策略统一放在分组，同组套餐遵守相同策略，不按购买来源叠加多套保号配置。

| 配置 | 规则 |
| --- | --- |
| 观看保号开关 | 按分组设置，沿用默认关闭的兼容边界 |
| 最低有效观看分钟数 | 最近 30 天累计门槛，允许分多天完成；新口径下默认值和取值范围待定 |

观察期和滚动统计窗口均为 30 天，不保留原来的可配置续期天数。保号套餐默认永久，表示没有固定到期日，但不代表无条件保留权益。观看达标不修改到期日，不累加天数，也不重置观察期。

### 2. 观察期与每日考核

- 首次购买保号套餐时，从本次购买开始计算 30 天观察期，与注册时间无关。
- 对应保号权益失效后，重新购买授予该分组权益的套餐，重新开始 30 天观察期；管理员手动恢复该权益时同样重置开始时间。
- 当前检查时间距离观察期开始不足 30 天时，跳过对应权益的保号考核；满 30 天后参与每日检查。
- 每天按最近 30 天累计有效观看分钟数判断，累计值大于或等于分组门槛即达标，低于门槛则对应权益失效。统计不能仅限于检查当天，也不是按固定月周期清零。
- 多个分组的观察期与资格分别维护，购买其他分组不重置本组观察期。
- 2026-10-05 补充确认：保号按用户的有效观看累计，不要求观看时正在使用被考核的分组。使用正常付费组期间，公益保号组继续独立考核，这段时间的有效观看同样计入保号累计；切换生效组不暂停考核或重置观察期。
- 同一用户的有效观看累计可用于其多个保号组，各组分别按自己的观察期和分钟门槛判断，不将观看分钟数在组之间分摊或消耗。已失效的组仍不能通过观看自动恢复。
- 调度、日期边界和外部本地时间解析统一使用 `CRON_TIMEZONE`；购买起算事件、30 天的精确时间边界和每日执行时点需在技术设计中收口。

### 3. 失效与恢复

- 不达标使对应保号权益失效，不能只修改 Emby 登录开关而保留一条仍被认定有效的永久权益。
- 失效后不能因后来观看达标、普通权益重算或 Policy 同步自动恢复；必须重新购买相应分组的套餐，或由管理员明确恢复该权益。
- 购买其他分组的套餐只授予相应权益，不恢复原来失效的保号权益。
- 某组失效但仍有其他有效组时，按已有等级规则选择生效组并同步资源权限；只有全部权益不可用时才禁用 Emby，始终保留未被人工停用的 Ember 账号登录及购买入口。
- 保号失效独立于人工账号停用或 Emby 人工禁用；购买或保号权益恢复不得绕过独立的人工限制。
- 失效历史和原因应保留供排障，不能通过删除用户或清空历史实现失效。

### 4. 模块与数据边界

- 分组管理 API/Web：维护两项保号配置。前端实现必须遵守 Ember 风格，设计与交互以[前端设计规范](../../reference/web-design-guide.md)为准，本计划不引入偏离规范的特例。
- 播放适配层：基于核实的版本化合同提供可追溯的有效观看事实、统计窗口及数据完整性结果，不直接修改权益。
- 权益服务：统一处理观察期、保号资格失效、购买重获和管理员恢复，将资格纳入有效分组选择，处理购买、恢复、换组、到期任务与保号任务的并发。
- 调度层：每日执行保号考核，复用权益重算和现有 Emby 同步职责；与自然到期任务的顺序及幂等边界在技术设计中确定，不增加请求时考核。
- 数据库：预计增加分组配置、分组权益的观察期起点和失效状态，以及必要的审计或处理进度。具体字段和表结构待设计，模型、索引或约束变化必须同步幂等 SQL migration，不能依赖 `AUTO_MIGRATE`。
- 所有有效权益消费者都必须识别保号失效，避免永久到期日使失效权益重新参与分组选择。Emby 同步沿用现有访问投影与人工限制边界，不能另建互相覆盖的账号开关。
- 对外字段使用 camelCase，列表使用 `data`，GORM 显式映射列名。具体 DTO/API 合同待技术设计，本轮不编写 SQL 或接口代码。

### 5. 关键流程与失败处理

1. 读取开启保号的分组及对应有效权益，排除仍处于观察期的权益；已失效权益不通过扫描自动恢复。
2. 通过已核实的数据源统计最近 30 天有效观看，校验数据完整性后与门槛比较。
3. 达标则保持权益；不足时，在权益写入边界重读分组配置、观察期起点及当前资格，避免旧扫描覆盖并发购买或人工恢复。
4. 保存统计证据、失效原因和处理结果，统一重算有效组，按既有链路同步 Emby 访问策略。

失败处理约束：播放数据缺失、协议无法确认、外部查询失败或结果被截断时，不得将未知结果当作零观看并批量失效；跳过受影响考核并记录失败原因。完整且有效的零观看结果才可用于判定不足。重试不能重复失效或重置观察期，远端同步失败不能被描述为已成功禁用。日志保留用户/分组标识、统计窗口、门槛、累计时长和失败点，不记录凭据或完整外部响应。

## 实现前待核对事项

本轮五项核心业务澄清已完成。以下为实施前待收口边界，不能当作已验证能力直接编码：

1. 按[播放合同](../../reference/playback-reporting-api-contract.md)和[用户策略合同](../../reference/emby-user-policy-and-item-route-contract.md)核对目标插件版本、权限、时间、错误及暂停/拖动语义。现有累计记录能否支持跨窗口播放的归属、多设备去重及足够完整的保号统计仍未证实；不凭字段名推断，不默认既有会话立即中断。真实验证须另行授权。
2. 明确购买起算对应的支付成功/权益履约事件，保证重复支付回调不重置观察期；确定兑换、管理员首次授予和存量权益启用策略时的起点，以及有效权益再次购买时的处理。
3. 确定 30 天按业务日还是连续时长计算、窗口上下界、跨日/跨窗口拆分、乱序晚到数据和用户绑定变化的处理，所有时间复用 `CRON_TIMEZONE`。
4. 收口有效观看适用的媒体类型及事实识别边界；已确认不限制观看时的生效组，同一观看累计可分别用于多个保号组，本轮未约定额外资源库限制。
5. 确定分组开关或门槛变更、限时权益与保号策略共存、存量数据迁移的处理规则。关闭保号是否恢复已失效权益不能默认推断；分钟数默认值不可直接沿用旧单日口径。
6. 收口每日调度时点、数据完整性判断、补查/重试范围、幂等审计和远端同步失败处理；不得擅自增加观察期之外的宽限规则。

## 验证方式

本轮仅检查计划、索引、相对链接及差异格式，不执行业务测试。实施时先用失败测试锁定状态流转；Go 外部依赖全部 mock，前端测试不依赖真实后端，涉及 Bot 时同样 mock 外网与 Internal API。

| 场景 | 验收预期 |
| --- | --- |
| 开关关闭、无目标组权益 | 不参与保号失效，不授予新组 |
| 注册已满 30 天，但购买不足 30 天 | 按购买起点跳过考核 |
| 观察期不足 30 天、恰好满 30 天 | 分别跳过、参与考核；按收口后的时间边界测试 |
| 多天多段观看累计恰好达到门槛 | 保留权益，不更新永久期限或观察期起点 |
| 窗口滑动后累计不足 | 对应保号权益失效，保存原因 |
| 暂停、拖动、跨窗口、多设备、重复记录 | 按核实合同统计，不虚增有效观看 |
| 权益失效后有新观看、普通重算或 Policy 同步 | 不自动恢复失效权益 |
| 重新购买同组套餐、管理员明确恢复 | 恢复对应权益，重置 30 天观察期 |
| 购买其他组套餐 | 只授予对应组，不恢复或重置原失效组 |
| 重复支付回调、任务重试 | 不重复发放、重置观察期或失效 |
| 多组共存、某个保号组失效 | 选择最高有效组，保留其他权益期限及观察期 |
| 正常付费组生效期间持续观看 | 观看计入公益组保号累计，公益组继续考核，不暂停或重置观察期 |
| 多个保号组门槛不同 | 同一观看累计分别比较各组门槛，可出现部分组达标、部分组失效 |
| 正常组到期，公益组分别处于有效/失效状态 | 前者回退公益组；后者不恢复公益组，无其他有效权益时禁用 Emby |
| 所有组失效 | 禁用 Emby，保留 Ember 登录和购买入口 |
| 人工停用或人工 Emby 禁用 | 购买和保号恢复不绕过独立人工限制 |
| 扫描与购买/恢复/换组/自然到期并发 | 旧结果不能覆盖新权益或观察期 |
| 查询失败、数据缺失/截断与完整零观看 | 前者跳过并记录；后者按门槛判断 |
| Emby 同步失败 | 本地资格与远端同步结果分别可追溯，不报告虚假成功 |
| 配置变更、存量迁移、晚到数据 | 按实施前收口的规则验证，不凭旧期限推断资格 |

实现阶段在 `services/api` 执行适用的 `go test`、`go vet ./...`、`go build ./...`；在 `services/web` 执行相应测试及 `npm run build`。按影响面补 mock 合同测试、数据库并发与迁移测试。真实 Emby 验收另行授权，不能将 mock 通过表述为外部链路已验证。
